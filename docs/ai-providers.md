# AI-провайдеры

## AI-провайдеры (проверка сочинений)
- Два OpenAI-совместимых провайдера в `server/ai.py` (реестр `PROVIDERS`, порядок `PROVIDER_PRIORITY`): приоритетный **CloseRouter** (`EGE_CLOSEROUTER_API_KEY`, `EGE_CLOSEROUTER_BASE_URL`, `EGE_CLOSEROUTER_MODEL`; Bearer-авторизация, system-промпт подклеивается к user-сообщению — маршрут anthropic роняет роль system) и запасной **gptunnel** (`EGE_AI_API_KEY`/`AI_API_KEY`, `EGE_AI_BASE_URL`, `EGE_AI_MODEL`; сырой ключ в Authorization + `useWalletBalance`). Новый ВСТРОЕННЫЙ провайдер = одна запись в PROVIDERS + место в PRIORITY.
- **Админка «Провайдеры»** (`#/providers` в `js/admin.js`, API `/api/admin/providers/*`): карточки всех провайдеров (встроенные + свои), приоритеты high/medium/low (один слот — один провайдер, `providers_set_slots`), выключатель, ручные пробы живым запросом «привет» (1 токен, троттлинг 3 с/15 с), добавление своего OpenAI-совместимого провайдера (id/base_url/model/api_key/auth/model_title/useWalletBalance/mergeSystem). Свои провайдеры хранятся в `app_config` (`ai_custom_providers`/`ai_provider_slots`/`ai_provider_enabled`/`ai_model_titles`), ключи — открытым текстом (осознанная цена: файл БД 0600 и хранит все сессии), клиенту ключ не отдаётся (только `keySet`/`keyHint`). Статус «Используется» = успех живого трафика за 60 с (`PROVIDER_RECENT_SEC`), холостых запросов нет. Недоступная модель добавлению не мешает — вернётся `warning`. Встроенные провайдеры удалять нельзя, только выключать.
- **Третий протокол — Anthropic Messages (`protocol=anthropic`).** Запрос `POST {base}/messages`, ключ в `x-api-key` + `anthropic-version` (Bearer не шлётся), `system` отдельным полем, история — блоки `tool_use`/`tool_result` (подряд идущие user-блоки склеиваются), tools — `input_schema`, `tool_choice` required→any, none — без tools; ответ `content[]` → chat-форма общим `parse_tool_message`. Мышление (effort) этим протоколом не задаётся. Проверка моделей перебирает протоколы: сохранённый первым, затем остальные — но только при прямом сигнале формата (слово `protocol` в теле ошибки или 404/405/415), иначе перебора нет. Дополнительные попытки ограничены `PROBE_FALLBACK_TIMEOUT_SEC` и общим бюджетом модели. Ответившая модель отдаёт свой `protocol`; админка ставит шаблон сама (при выборе модели из пинга и после «Проверить»), сохранение закрепляет. Заголовки (`extra_headers`) шлются при любом протоколе — без `x-opencode-session` шлюз Go не пускает ни один формат. Живой случай 07.10: `claude-haiku-5-5` на opencode отвечает только по `/messages`.
- **Свой провайдер по Responses API (opencode).** Шлюз без chat-протокола: на `POST /v1/chat/completions` отвечает 400 `ModelProtocolUnsupported`, работает только `POST /v1/responses` (`instructions` + `input`, ответ массивом `output[]`). Поэтому у своего провайдера есть необязательные поля сверх chat-набора: `protocol` (`chat`|`responses`), `reasoning_effort` (`minimal`|`low`|`medium`|`high`, пусто = default шлюза) и `extra_headers` (статика, до 8; `Authorization`/`Content-Type` переопределить нельзя; секретам там не место — значения видны в админке). Транспорт приводит ответ к chat-форме (`_responses_to_message` → общий `parse_tool_message`), дальше контракт един: история треда уходит `function_call`/`function_call_output`, tools — плоскими function-объектами, `max_tokens=1` от проб поднимается до `RESPONSES_PROBE_MAX_TOKENS` (512 — reasoning съедает единицу целиком, и живой провайдер выглядел бы мёртвым), пробы всегда идут на `minimal`. Мышление разъезжается по путям: ИИ — `minimal` явно из `_agent_chat_fn` (замер 04.10: 38 токенов против 462 на high при том же ответе), судья сочинений — `high` по умолчанию `as_judge` (измерение обязано думать в полную силу). Админка: шаблон протокола — сегмент из двух (`OpenAI`/`Responses API`, тот же `.a-seg2`, что приоритет) на странице добавления и в quirks существующего своего (встроенные — всегда chat, им сегмент не показывается); выбор шаблона прячет/показывает блоки (заголовки и подсказка про instructions — только у Responses, подклейка system — только у OpenAI; значения скрытых не стираются, при возврате на месте); мышление — сегмент из 5 везде (`Стандарт` = default шлюза, поле не едет); заголовки — строки тем же `.a-chain-row`, значения видны (секретам там не место); чип Responses в списке и на странице; черновик «Проверить без сохранения» идёт выбранным протоколом. Живой урок: Cloudflare перед шлюзом режет дефолтный `Python-urllib` UA кодом 1010 всегда, а любой не-urllib (хоть `ege-2026`) проходит всегда — поэтому у записи лежит `User-Agent` в `extra_headers`; глобальный UA транспорта не меняем, чтобы не трогать денежные пути остальных провайдеров. Регресс — `python3 test/responses-protocol.py` (wire-формат, маппинг tools туда-обратно, effort по путям, пробы, валидация; офлайн, temp-БД).
- **Стандартные приоритеты материализуются, а не подразумеваются кодом** (`ai.ensure_default_slots`, вызывается из `providers_overview`, `providers_set_slots`, `custom_provider_create`): closerouter = «Высокий», gptunnel = «Средний» — ровно то, что делает `PROVIDER_PRIORITY`. Пустые слоты были не просто неудобны: карточки врали о порядке (ротация всё равно шла closerouter → gptunnel), и это давало ДЫРУ — поставив СВОЕМУ провайдеру «Высокий», админ получал двух претендентов на первый слот, потому что «стандартный» приоритет был неявным. Запись идемпотентна и срабатывает только когда не занят НИ ОДИН слот (освободившийся нарочно админ не теряет). После материализации смена приоритета карточкой освобождает прежний слот явно.
- **Два направления маршрутизации: обычные и Plus — одинаковый функционал, разный конфиг.** У каждого тира ПОЛНЫЙ свой конфиг (провайдеры, слоты, выключатели, цепочки, названия, активный, судья, fails): free живёт на исторических ключах без суффикса (миграции нет — текущие настройки и есть free), plus — `ai_plus_*` и стартует клоном free при первом обращении (`ensure_tier_clone`, идемпотентно; пустое осознанно не перезатирает), дальше независим. Встроенные провайдеры (ключи из окружения) общие и видны в обоих вкладках. Весь слой `ai.py` принимает `tier` явно (`None` = free — старое поведение без правок вызывающих); молчаливый free при пропущенном тире был бы чужой маршрутизацией, поэтому класс багов «тир не в тот позиционный слот» (поймано живьём: `probe_models_stream(pid, wanted, tier)` клал tier в `budget`) давится AST-гардом в тесте — tier только по имени. Метки здоровья keyed `(tier, pid)`; фоновая проба идёт по обоим тирам; события в ленту помечаются ` [Plus]` (free без суффикса — старые тексты не тронуты); статус-страница агрегирует (максимум меток, роутер free) без смены контракта. Сервер решает тир по подписке (`ai_tier_for`: активна → plus, иначе free) в трёх точках — ход, подтверждение, проверка сочинения — и дальше тир не меняется внутри запроса; админские ручки берут тир из query (`?tier=`, DELETE/GET) или тела, аудит помечает Plus. Админка: табы «Обычные | Plus» тем же `.a-seg`, тир в localStorage (глубокие ссылки открываются в нём), все вызовы несут тир, страница провайдера пересобирается при смене вкладки. Миграция проверена живьём: после рестарта plus = free один в один (те же 5 провайдеров, слоты, судья opencode). Регресс — `python3 test/ai-tiers.py` (изоляция записей/слотов/судьи/роутера, трафик в URL своего направления в обе стороны, failover не трогает чужой active, AST-guard, `ai_tier_for` по подписке; офлайн, temp-БД) + секция P2c в `test/admin-providers-ui.js` (табы, создание/судья/слот/удаление в Plus сквозь UI, free не задет).
- **Клик по карточке открывает ОТДЕЛЬНУЮ СТРАНИЦУ провайдера** (`#/providers/<id>`, `screenProviderPage`), и список моделей берётся У ПРОВАЙДЕРА. Модалка была тупиком: настроек много (модель, название, адрес, ключ, quirks, приоритет, список моделей, пинг), в широком блоке поверх списка они не помещались, а на телефоне она превращалась в одну колонку с обрезанным низом. Страница даёт сетку из двух колонок (настройки | состояние и опасная зона), свой адрес (работает «назад», ссылку можно отправить) и закреплённую панель действий со отметкой «есть несохранённые изменения». **Важно:** `screenProviders(true)` (тихий рефреш списка) со страницы НЕ пересобирает каркас — иначе после сохранения человека выбрасывало в список, стирая вердикт проверки и напечатанные поля (поймано браузерным тестом). **Прямая ссылка/перезагрузка на странице тоже работает:** роут догружает список молча (`if (!Prov.data) await screenProviders(true)`, тот же приём, что у `providers-new`) — раньше список в памяти был пуст, и любая перезагрузка давала «Провайдер не найден» (поймано браузерным тестом: reload на странице заново показывает `#provDetailModel`). Страница (`.a-page-*`): шапка (точка статуса, id, чипы «свой/встроенный/активный/выключен/модель изменена», строка статуса), тематические секции — «Модель» (ID + название для ученика + три кнопки), «Модели провайдера» (список + рейтинг), «Подключение» (Base URL, ключ), «Место в очереди» (сегмент приоритета) — и закреплённый подвал со сбросом и «Сохранить и проверить». Разметка: `GET /api/admin/providers/<id>/models` → `GET <base>/models` (`ai.list_models`) — единственный честный источник имён (свой список id в админке означал бы угадывание; текущая модель в ответе всегда первая, `MODELS_LIST_MAX` = 400), выбор модели, её проверка до применения (`POST .../probe-model` → `ai.probe_model`) и применение `POST .../apply` (`ai.provider_set_override`) с автоматической проверкой применённого. Строка списка — `.a-model` (точка вердикта, имя, чип задержки/«сейчас»), фильтр — `#provModelFilter`, чипом «сейчас» и галочкой выбранного, а НЕ нативный `<select size=8>`: он выглядел в админке как чужой старый дизайн и не давал ни фильтра, ни отметки. Имя модели идёт в `data-model`, а не в `onclick` — в кавычках вида `владелец → "модель"` ломал атрибут и всю страницу до ошибки JS (поймано браузерным тестом). **Кнопка сброса есть у обоих типов, и «стандартное» у них разное по источнику:** встроенный → снова значения из окружения (деплой остаётся истиной, сносятся все переопределения из `ai_provider_overrides`), свой → снимок `entry["defaults"]`, сделанный при добавлении (без него «сброс» откатывал бы к ПОСЛЕДНЕЙ правке, то есть ничего); сброс снимает и название снятой модели, иначе подпись «временная» висела бы на модели, которой у провайдера больше нет. Метка ручной проверки при смене модели/сбросе гасится — она мерила другую конфигурацию. **Троттлинг проб разведён по кнопкам** (`probe-model:<id>` против `one:<id>`): общий бакет давал бы 429 двум соседним кнопкам в одной панели, а это разные вопросы к провайдеру; список моделей троттлится отдельно (5 с на провайдер, 20 с на все). Клиент читает `retryAfter` из ответа и пишет «подожди N с» вместо «ошибка» (`AdminApi.request` прокидывает поле на Error).
- **Живой пинг моделей: строка появляется, как только модель ответила.** `POST /api/admin/providers/<id>/probe-models-stream` (`ai.probe_models_stream`) отдаёт **NDJSON-поток**, клиент читает его `fetch` + `response.body.getReader()` и дорисовывает строки. Почему NDJSON, а не SSE: `EventSource` не умеет ни POST, ни заголовки, ни нормальную куку админки. События: `start` (список моделей — сразу рисуются строки «проверяем», а не пустой экран), `result` по одной модели, `done` (итоговый `order`). **Жёсткий бюджет 20 с** (`PROBE_MODELS_BUDGET_SEC`, у клиента — счётчик времени в шапке блока): что не успело — получает честное «не ответил за 20 с», а не тишину; у любого шлюза найдётся висящая модель, и без бюджета пинг превращался бы в ожидание неизвестной длины. Потоки не дожидаются: `pool.shutdown(wait=False)` в `finally`, иначе соединение висело бы до последнего таймаута шлюза. Бюджет поднят с 10 с: медленные шлюзы (вроде funpay) отвечают дольше 10 с, и короткий бюджет метил их мёртвыми. Замер на стенде: первая живая строка на 0.03 с, потолок ровно 20.0 с, висящая модель помечена. Во время проверки строки идут в порядке ОТВЕТОВ (видно, как приходит), по завершении список пересобирается ПО СКОРОСТИ — это и есть обещанное «от быстрых к остальным». Троттлинг общий с пакетной проверкой (`probe-models:<id>`, 22 с), поэтому «подожди N с» приезжает обычным событием `error` (клиент уже читает поток, а не HTTP-статус). Рейтинг — `.a-rank` (номер/спиннер, точка, имя, полоса задержки, мс или причина), появление строк анимировано, `prefers-reduced-motion` уважается. Название модели — всегда целиком, своей строкой сверху (вторая строка — номер, точка, полоса, задержка): раньше имя упиралось в `max-width` и резалось после точки, и было непонятно, что проверялось; то же у строк списка `.a-model`.
- **Сохранение мгновенное: сервер НЕ спрашивает шлюз после apply.** Раньше `POST .../apply` (и добавление провайдера) дёргали живой пробой модели, поэтому кнопка «Сохранить» ждала ответа провайдера — до 20 с на мёртвой модели, то есть подтверждать настройку можно было только дождавшись шлюза, ровно тогда, когда он не нужен. Проверка — отдельный вопрос админа: на странице есть «Проверить» и «Пинг всех моделей», в форме добавления — «Проверить без сохранения». Ответ `apply` теперь `{ok, provider}` без `probe`/`warning`.
- **Добавление провайдера — тоже СТРАНИЦА** (`#/providers-new`, `screenProviderNew`), а не модалка `.a-modal`: полей много, и в узком блоке поверх списка они не помещались, а на телефоне низ срезался. Та же сетка, что у страницы провайдера: слева «Подключение» и «Модель», справа «Место в очереди» (сегмент), «Особенности шлюза» (quirks) и «Что будет после сохранения» (честно говорит, что сохранение мгновенное и проверять надо на странице). Занятые слоты видны в шапке из актуального списка — иначе подсказка «слот свободен» соврала бы. Обязательные поля проверяются у себя в поле, а не ответом API после нажатия. После добавления сразу открывается страница нового провайдера. Маршрут отдельный (`providers-new`), а не `#/providers/new`: `new` может быть настоящим id провайдера. `navigate()` на тот же адрес вызывает `render()` сам — иначе повторный переход молча ничего не делал.
- **Панель действий и честные отметки на странице.** Сохранение одной кнопкой едет всё сразу (`model`, `model_title`, `base_url`, `api_key`, `slot`, `use_wallet_balance`, `merge_system`) — иначе модель применилась бы мгновенно, а слот после второго запроса, и между ними ученик получил бы провайдера по старому порядку. `provDetailMarkDirty` показывает «не применено» под полями и «есть несохранённые изменения» в закреплённой панели: выбор модели из списка или из рейтинга — это правка, а не применение, и без подсветки админ уходил со страницы, думая, что настройка действует. **Сброс остаётся на странице** (результат надо увидеть), **удаление уводит в список** (настраивать больше нечего). Типичные грабли геометрии, пойманы скриншотами: прокрутка не должна заезжать под шапку (нужен непрозрачный фон), крестик/бейджи не должны утаскивать друг друга при переносе на 390px, а класс завершения пинга надо вешать на сам блок `.a-ping`, а не на обёртку — иначе «готово» не наступает визуально.
- **Название модели для ученика задаёт админ, в коде имён моделей нет.** В `server.py` был вшитый словарь `{"closerouter": "Claude Sonnet 5", "gptunnel": "Qwen Flash"}`: любая другая модель подписывалась чужим именем, а свой провайдер молчал (его id в словаре не было, строка просто не рисовалась). Теперь название лежит в `app_config.ai_model_titles` = `{providerId: {modelId: "название"}}`, поле в панели рядом с ID модели, при смене модели название вводится заново (старое остаётся у своей модели — подписывать новую модель чужим именем нельзя). На экране результата (`ege-result.html`, `data.provider`) подпись собирается через `_AI.model_student_label(provider, model)` — она отдаёт ТОЛЬКО название админа, иначе пусто: строка «проверено моделью grok-chat-fast» была бы шумом из технического id, поэтому без названия строка просто не появляется, а служебные id уезжают в `providerId`/`model` (диагностика, не показ). Админ не пропускает это молча: у модели без названия на карточке горит чип «нет названия», а в панели — подсказка. У админской подписи откат на id есть — это `_AI.model_display_title`. Неизвестный провайдер и легаси `ai+grammar` строку не рисуют вовсе. Какая модель ОТВЕТИЛА, фиксируется thread-local `_chat_state.model` + `ai.last_used_model()` и пишется в `essay_checks.model` / `essay_check_history.model` / `essay_submissions.evaluation_model` (идемпотентные `ALTER`; если колонки нет — пишем старую форму запроса и не падаем) — подпись обязана называть ту модель, что ответила, а не текущую по конфигурации (failover мог переключить и модель). Регресс — `python3 test/model-title.py`.
- **Две разные проверки, и путать их нельзя.** «Проверить всех» в разделе (`POST /api/admin/providers/probe-all`, клиентский `runPingAll`) — это ЖИВЫЕ ПРОВАЙДЕРЫ: запрос «привет» каждому по очереди, строка на провайдера (точка, имя, слот, задержка в мс или причина), результат лежит в `Prov.ping` и переживает перерисовку раздела. «Пинг всех моделей» на странице (`POST .../probe-models-stream` → `ai.probe_models_stream`, живой NDJSON) — это МОДЕЛИ ОДНОГО провайдера: у шлюза список на сотни позиций, доступны единицы (модель снята, нет доступа к региону), ручной перебор по одной — минуты. Сервер проверяет их пачкой по порядку провайдера (текущая модель первой), кап `PROBE_MODELS_MAX` = 30 за нажатие; **список сервер берёт САМ у провайдера**, а не берёт из тела запроса — клиент мог бы прислать что угодно, а проверять надо реальные модели. Ограничение объявляется в ответе (`skipped`, `limit`) и в шапке результата, а не молча обрезается. **Проверки идут ПАЧКОЙ** (`PROBE_MODELS_WORKERS` = 6 потоков) и отдаются потоком по мере готовности (см. ниже); пакетный `POST .../probe-models` остался для тестов и программных вызовов. Сервер возвращает готовый `order` (живые по возрастанию задержки, затем мёртвые), и клиент рисует рейтинг `.a-rank` ровно в этом порядке — строка кнопкой (выбирает модель прямо из результата), те же точки видны в списке моделей после проверки.
- Активный провайдер хранится в `app_config.ai_router` (JSON: active, lastError, lastProbeAt, fails; in-memory кэш на процесс). Отказ активного (баланс/401/403/таймаут/HTTP-ошибка — т.е. `AIError`/`AIUnavailable`) молча переносит запрос на запасного в том же вызове `chat()` и переключает активного; ученик ошибки не видит, максимум ждёт дольше (таймаут попытки — `EGE_AI_TIMEOUT_SEC`, по умолчанию 45 с: двойной запас над замеренными 10–21 с обоих провайдеров). Ошибка ФОРМАТА ответа (`AIFormatError`) failover не делает — провайдер ответил, жаловаться не на что. **Два подряд отказа понижают провайдера в конец очереди** (`_provider_demoted`, счётчик `fails` в той же строке, переживает рестарт): следующие запросы идут сначала на живых и не ждут его таймаут, первый же успех снимает понижение. Замер живьём 03.10: висел funpay (таймауты), флапали closerouter (то 5 с, то TimeoutError) и telegram (то 3 с, то 429) — без понижения каждый флип активного стоил запросу до 45 с ожидания мёртвого шлюза первым.
- **Судья проверки сочинений закреплён и не едет вместе с роутером.** Проверку содержания (К1–К6) ведёт фиксированный провайдер — `chat(messages, as_judge=True)` / `chat_json_as_judge` (формат «essay» в `FORMATS` указывает его полем `chat`), а не «тот, кто первым ответил» в общем порядке. Причина измерена: в конфиге было три настроенных провайдера с ТРЕМЯ РАЗНЫМИ моделями (kimi-k3, claude-opus-5.5, anthropic/claude-opus-4.6), а бесшовный failover менял судью молча — один и тот же текст одного ученика дал **21, 21, 3, 3 из 22** (4 прогона подряд на живом коде). Разница видна в комментарии К1: дорогая модель пишет «позиция отвечает именно той проблеме» (10/10 содержания), дешёвая — «позиция по другой проблеме» (3/10). Это не стохастика: у одного судьи разброс ±1 (замер 22/22/22 и 21/21/21/21), а 18 баллов давала именно смена модели. Правило: **failover обязан сохранять доступность, но не имеет права менять измерительный прибор**. ИИ (`chat_with_tools`) и служебные пробы пинятся НЕ должны — им важна доступность, а не воспроизводимость измерения.
- **У судьи своя ротация, независимая от `ai_router`:** `judge_provider()` = явное назначение админа (`app_config.ai_essay_judge`) → автопереключение после отказа (залипает, `auto`) → приоритетный по слотам (`effective_priority()[0]`). Запасной (`judge_fallback`) подключается только при полном отказе судьи, и это событие уходит в ленту обращений (`judge_switch`: «Баллы, выставленные разными моделями, напрямую несравнимы»). `probe_tick` ротирует только основной роутер и **больше не переставляет судью у ученика на ходу**; он же возвращает прежнего судью, когда тот ожил (`_probe_judge_return`, тот же интервал 15 мин). Автопереключение снимает таймаут на мёртвый шлюз у каждой следующей проверки (без него отказ судьи стоил бы 45 с каждому ученику). Админка: карточка «Судья проверки сочинений» в разделе «Провайдеры» (`provJudgeCardHTML` + `POST /api/admin/providers/judge`, аудит `providers.judge`), поле `essayJudge` в `providers_overview`.
- **`ai_essay_judge` в `app_config` — не кэш, а настройка:** `{}` — судья по умолчанию (приоритетный), `{"provider": id}` — выбор вручную, `{"auto": id, "from": id}` — подмена после отказа. Ручное назначение автопереключением не перебивается, снятие назначения его заодно сбрасывает.
- Фоновый поток `start_failover_loop` (стартует в `run_server`) раз в **15 минут** (`EGE_AI_PROBE_INTERVAL_SEC`, дефолт 900) проверяет кандидатов СТРОГО ВЫШЕ активного («привет», 1 токен) и поднимает высшего живого; успех → он снова активен. Раньше пинался только приоритетный: при трёх провайдерах (high+medium лежат, работает low) medium после восстановления никто не проверял, и трафик шёл на low первым. Час был слишком долго: closerouter отвечает флакующим 400, и один отказ уводил его в запасные на целый час при живом провайдере. **Проба не грузит провайдера, когда он и так активен:** `probe_tick` выходит сразу при `current == preferred` — запрос уходит только когда активен запасной (проверено тестом: 15 минут без единого вызова к активному closerouter). Активного и более низких проба не дёргает вовсе (здоровье активного видно по живому трафику; вниз двигает только отказ в запросе). Отказ провайдера сам двигает lastProbeAt, так что интервал отсчитывается от последнего плохого сигнала. Проба не тратит пользовательский бюджет и не трогает активного при собственном отказе. Регресс трёхпровайдерного подъёма и понижения — новые секции `python3 test/ai-failover.py` (74 проверки).
- Провайдер без ключа просто пропускается: без `EGE_CLOSEROUTER_API_KEY` всё работает на gptunnel как раньше.
- Смена активного и восстановление — не только строчка в логе: они попадают в ленту обращений с таблеткой «Система» (см. раздел «Системные обращения»). Текст собирает сервер, роутер отдаёт только факт.
- Статус ИИ на странице `/status` — три строки (`agent`, `agent-tools`, `ai-providers`), и все три читают только прошлое, живых проб при загрузке нет: движок — `agent.public_agent_health()` (каждый инструмент из `AGENT_TOOLS` покрыт реализацией: read — одноимённой функцией, action — парой `propose_action`/`apply_action`), провайдеры — `ai.public_ai_health()` (in-memory метки последнего успеха/ошибки + переживающие рестарт персистентные метки `marks` в состоянии роутера и скаляры `ai_router.lastErrorAt`/`lastOkAt`; побеждает последняя запись, записей нет — честное «нет данных», а не зелёное). Живой случай 04.10: весь трафик шёл в Plus-тире, а роутер читался только free — после каждого рестарта (in-memory метки стирались) stale-ошибка free побеждала свежий успех plus, и страница врала «не работает», хотя ИИ отвечал. Теперь роутер и метки берутся максимумом по обоим тирам, метки успеха/ошибки пишутся в БД тем же апдейтом роутера (отдельных записей нет), а ручная проба из админки в метки живого трафика больше не пишет (только `lastCheck`) — иначе пинг мёртвой модели красил бы статус красным при живом обслуживающем провайдере. Удаление провайдера сносит и его метки, иначе мёртвый id вечно лежал бы в агрегате. Успехи persist'ятся наравне с ошибками: раньше рестарт стирал успехи из памяти, а древняя `lastErrorAt` снова красила статус красным. Страница `status.html` сама опрашивает `/api/status` раз в минуту (в фоне вкладки — нет; лимит 60/мин это не замечает). Наружу — ни ключей, ни адресов, ни моделей, ни текстов ошибок, возраст подписывает сервер (`_age_ru`). Подписки в статусе нет осознанно (биллинг ≠ работа сервиса). Регресс — `python3 test/status-agent.py`.
- **Минутные самопроверки страницы статуса (`server/health_checks.py`, только stdlib).** Раз в 60 с фоновый поток (`start_loop` в `run_server`, рядом с пробой failover) прогоняет 5 коротких проверок по разделам, которые видят пользователи, — `api` (хранилище отвечает, каталог не пуст), `content` (темы/задания/уроки), `agent` (все инструменты покрыты реализациями), `ai` (провайдер настроен, ротация не пуста, последнее известное по тем же слитым меткам + heartbeat фонового дозора), `essays` (таблицы на месте, рубрика загружена, судья назначен). Отдельной технической таблицы на странице НЕТ (ученику не нужны «мс», «рубрика v6» и «судья назначен»): свежесть прогона вшивается в строки «Что работает» полем `checkAge` («Отвечает • последняя проверка: только что»), упавшая проверка гасит свои строки (`_CHECK_FOR_SERVICE`), а провал `essays` добавляет строку «Проверка сочинений». Нового анонимного эндпоинта нет — значит, и новых лимитов не нужно: страница опрашивает тот же `/api/status` раз в минуту, как раньше. Проверки идут СТРОГО ПОСЛЕДОВАТЕЛЬНО (по одной): параллельный залп каждую минуту давал бы пилу нагрузки на SQLite с одним писателем, а выигрыш — доли секунды (каждая проверка — миллисекунды локальной работы). Проверки только читают (короткие read-only SELECT, ни одной записи/квоты/сессии) и НЕ делают живых вызовов: ни «привета» провайдерам каждую минуту (деньги + rate limit шлюза; живой сигнал — реальный трафик и проба раз в 15 мин), ни пинга LanguageTool (чужая доступность). Прогона нет первые секунды после старта — суффикса свежести тогда нет, а не врёт.
