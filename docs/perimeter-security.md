# Периметр: кто вообще может достучаться (после инцидента с открытыми портами)

## Периметр: кто вообще может достучаться (после инцидента с открытыми портами)
- **Приложение слушает только loopback.** `EGE_HOST=127.0.0.1` в `ege-2026.service`; наружу торчит только nginx (80/443). На `0.0.0.0` сокет приложения доставался из интернета напрямую — мимо TLS, HSTS и лимитов фронтенда. Правило: **приложение не публикуется никогда**, nginx — единственная точка входа.
- **Доверие `X-Forwarded-*` решает СОКЕТ, а не флаг.** `_peer_is_trusted_proxy()` требует и `EGE_TRUSTED_PROXY=1`, и loopback-адрес сокета. Одного флага мало: он означает «у меня есть прокси», а не «это соединение пришло из него». При `0.0.0.0` любой клиент подставлял `X-Forwarded-For` сам и **выбирал себе бакет всех лимитов** (300/мин, сетка `ai_take`, анти-лава по куке/сети, поддержка) — и мог выключить `Secure`-флаг кук подменой `X-Forwarded-Proto`.
- **nginx перезаписывает `X-Forwarded-For` на `$remote_addr`, а НЕ `$proxy_add_x_forwarded_for`.** `$proxy_add_x_forwarded_for` дописывает реальный адрес к присланному клиентом, и бэкенд берёт первый элемент цепочки — то есть подменённый. Только `$remote_addr` даёт цепочку, которой нет.
- **Один адрес клиента — одна функция.** `client_ip(handler)` — единственный источник IP для всех лимитов и отпечатков (`socket_ip` для сокета, `trusted_forwarded` для заголовка за доверенным прокси). Раньше `auth_login_allowed`, `admin_login_allowed` и лимит `/api/status` брали сырой `client_address[0]` = всегда `127.0.0.1` за nginx, то есть **один общий бакет на весь интернет**: 11 чужих запросов запирали вход всем, включая админку. Мусорный `X-Forwarded-For` (`unknown`, SQL-строка) не становится ключом бакета — значение проходит через `ipaddress.ip_address`.
- **CSRF-гейт один и на всех.** `guard_csrf(path)` стоит в начале `do_POST/do_PATCH/do_PUT/do_DELETE` для любого `/api/`. Раньше `support_request_is_same_origin()` стоял только на трёх точках входа, а остальные ~20 изменяющих состояние эндпоинтов держались единственного `SameSite=Lax` — то есть оборона жила в браузере, а не на сервере. Клиент без `Origin` (curl, тесты, приложение) пропускается: автоматической отправки кук чужой страницей у него нет.
- **Хост из заголовка проверяется.** `X-Forwarded-Host` читается только через `trusted_forwarded`, а в `Location` редиректа и в `public_base_url` (sitemap) попадает только валидное DNS-имя (`_is_plain_host`) с числовым портом — иначе `Host: x/<url><loc>…` дописывал произвольный XML в карту сайта.
- **NUL в пути — тихий 404.** `Path.resolve()` бросает `ValueError` на `\x00`, а не `OSError`, и запрос падал трейсбеком без ответа; статика вне `/api/` лимитом не покрыта, то есть это был ещё и усилитель мусора в логах. Ловятся и `stat()`, и `read_bytes()`.
- **`/api/auth/*` под общим лимитом.** Общего per-IP бакета у них не было вовсе, а `auth_login_allowed` считает только неудачи; `register` заводил строку `users` ДО проверки дубля, поэтому скрипт без кук множил аккаунты-переростки.
- **Вход не выдаёт время наличия адреса.** Неизвестный email отвечал мгновенно (PBKDF2 не считалась), неверный пароль — после 210k итераций: одинаковый текст 401 обесценивал себя. Теперь при отсутствии строки/пароля считается `_TIMING_EQUALIZER_HASH`.
- **nginx — второй слой.** `conf.d/ege-hardening.conf`: `server_tokens off`, `limit_req` (30 r/s на адрес; 1 r/s на вход и админку), `limit_conn`. В `sites-available/egeeasy.ru` — `deny all` на `/.`, `/server/`, `/test/`, `/deploy/` и на `*.sqlite3|*.bak|*.log|*.env|*.md|*.py`. Правила срабатывают ДО проксирования, то есть работают даже если бэкенд снова окажется доступен извне.
- **Файлы с секретами — 0600, каталоги 0700.** `UMask=0077` в unit: БД, бэкапы и `-wal/-shm` больше не создаются `0644` в корне сайта (там лежат все живые сессии и хеши паролей).
- **ufw: default deny incoming**, разрешены 22, 80, 443. fail2ban (`jail sshd`, 5 ошибок/10 мин → бан на час) против перебора root-пароля: за сутки до его установки было ~68 тыс. неудачных попыток, 9 944 с одного адреса.
- **Секреты админки — только из окружения.** `EGE_ADMIN_PASSWORD_HASH` (pbkdf2_sha256) читается из `/etc/ege-2026.env` (0600), встроенного хеша нет — без переменной сервер не стартует. `EGE_ADMIN_COOKIE_SECURE=1` держит `Secure` у кук безусловно, а не по заголовку прокси.
- **Второй фактор входа в админку — Telegram (`server/telegram.py`, только stdlib).** При заданных `EGE_TELEGRAM_BOT_TOKEN` + `EGE_TELEGRAM_ADMIN_CHAT_ID` верный пароль сессию НЕ открывает: создаётся заявка `admin_login_pending` (токен — только sha256, как сессии; TTL 5 мин, живые капы 3/браузер и 5/IP), владелец получает код/IP/время/клиента с кнопками «Подтвердить/Отклонить», браузер ждёт опросом `GET /api/admin/login/status`. Решение из чужого чата игнорируется, молчание и просрочка — отказ. Без обеих переменных вход остаётся парольным (осознанно, не тихий отказ). Опрос сам втягивает getUpdates (`telegram_ingest_updates`, идемпотентно, offset в `app_config`) — запасной путь, если фонового цикла нет (тесты). Основной путь — фоновый long-poll цикл `admin_telegram_loop` (старт в `run_server`, стоп по событию, при мёртвом Bot API пауза растёт до 5 мин): решения и `/start` применяются всегда, а не только во время чужого входа. Опрос статуса — long-poll 20 с (`ADMIN_LOGIN_STATUS_WAIT_SEC`, клиент держит запрос 45 с и сразу опрашивает снова): решение применяется в момент нажатия, сайт открывает сессию мгновенно. Неслание сообщения откатывает заявку (503 `TELEGRAM_UNAVAILABLE`). `/start`/`/help` получают ответ о привязке чата (чужому — только его id, обычный текст игнорируется молча). Сообщение правится при ЛЮБОМ исходе (подтверждено/отклонено/время вышло/отозвана — мёртвых кнопок нет), на кнопке — тост с итогом. Регресс — `python3 test/admin-telegram.py` (фейковый Bot API через `EGE_TELEGRAM_API_URL`: парольный путь без бота цел, заявка без куки, чужой браузер/чат, deny/expire/cancel, капы, офлайн-бот).
