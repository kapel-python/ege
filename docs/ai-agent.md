# ИИ

## ИИ
- Персональный ИИ — экран SPA (`#/ai`, `screenAgent` в `js/agent-spa.js` + `css/agent.css`, в навигации «ИИ» левее «Профиля»): ученик пишет вопрос, модель сама ходит по базе его прогресса через tool-calling и отвечает по реальной истории; каждый шаг виден (лента «Шаги» с иконками чтение/действие/применено + «Подробнее» с аргументами и результатом, во время хода — скелетоны). Своей страницы/шапки/темы/тостов/модалок у раздела нет: топбар, сайдбар, тема, тосты и диалоги — общие с остальными разделами (поэтому шапка на «ИИ» та же и уже готова при переходе). Текст только через `textContent`. Раздел доступен зарегистрированным; доступ и лимиты — через подписку Plus (`users.subscription` зеркалит статус для глаз, лимиты читают таблицу `subscriptions`; бесплатно раздел закрыт флагом `EGE_AGENT_REQUIRES_PLUS` — 403 `SUBSCRIPTION_REQUIRED`, с Plus — 50 ходов/день). Старые адреса `/agent` и `/ai` — редирект-заглушка в `agent.html` на `/dashboard#/ai` (с пробросом `#/thread/<id>` → `#/ai/<id>`); сервер их маппит как раньше, но полной страницы там больше нет.
- Сзади — цикл, а не один запрос: `server/ai.py` (`chat`/`_chat_via` принимают `tools`, wire — OpenAI `tools` (явный `tool_choice` не шлём, умолчание и есть auto), парсер `parse_tool_message` допускает реплику рядом с вызовами (она уходит в `preamble`, вызовы главнее — см. следующий пункт)), `server/agent.py` — инструменты и цикл `run_cycle`. Чтение (без подтверждения): `fold_web(op=progress|profile|skills|errors|attempts|daily|history|forecast)` + `lesson_get`/`task_get`/`essay_history`/`plan_get` (текущий план: есть ли, название/срок/прогресс/периоды с темами — в том же формате, что `plan_draft`, periods годятся в `plan_apply` как шаблон)/`plan_draft` (черновик плана детерминирован по прогнозу). Действия (только с подтверждением): `update_profile` (имя/уровень/цель; `goal_set` слит сюда — цель поле профиля), `resolve_error` («разобрался»), `reset_progress` (сброс предмета), `plan_apply` (применить учебный план: черновик `plan_draft` на гибкий срок 1–365 дней собирается в периоды с темами/уроками/заданиями, proposal строг — чужие skillId и не сумма дней чинятся моделью в том же ходу; состояние, гейты закрытия тем (время — конец периода — ИЛИ освоение ≥ 75) и HTTP `GET /api/plan` + `POST /api/plan/topics/close` — в `study_plan_*`). `push_task` нет осознанно («домашки» как сущности нет — план отдаётся текстом), `essay_recheck` нет осознанно (перепроверка тратит квоту сочинений и остаётся явным выбором на `ege-result.html`; агент показывает историю, но чужую квоту не тратит). Системный промпт — русский, числа из инструментов или стартового блока хода (имя, предмет словами и компактный прогноз кладёт туда сервер через `turn_system`, поэтому «как меня зовут» и «какой у меня предмет/прогноз» не стоят вызова; `fold_web(op="forecast")` — только за деталями), формула прогноза серверная = браузерной (теория 40 + практика с затуханием 45 дней (ошибки — 14, прощение), весом подсказки как в XP (0.6/0.3) и звёздами сложности напрямую, насыщение 12, вилка ±hw, топ по приросту — иначе экран и агент называли разные баллы), константы сверяет тест с js/state.js, имя без угадывания рода, коротко. Стартовый блок хода через `turn_system` несёт и одну строку про план («Учебный план есть: …» / «Учебного плана пока нет»): при пустом плане «сделай план» идёт сразу в `plan_draft` без лишнего `plan_get`, при существующем модель знает, что детали надо добрать инструментом.
- **Реплика + вызовы — не ошибка формата (живой случай 29.09).** gptunnel/qwen3.8-flash на вопрос «вызови все доступные инструменты» отвечал `content="Сейчас соберу полную картину по тебе…"` ВМЕСТЕ с `tool_calls` (3 ответа из 3; closerouter на том же вопросу — пустой content). Строгий разбор давал `AIFormatError` → невидимый повтор при temperature 0 приносил тот же смешанный ответ → ход падал в 502 «ИИ не смог ответить», а тред оставался пустым (ни вопроса, ни шагов). Теперь вызовы главнее, текст уходит в `preamble`; ответом ход считается по-прежнему только сообщение без вызовов. **Потолок шагов тоже не отказывает:** `MAX_TOOL_STEPS` добрал данных → `agent._summarize` делает ОДИН вызов без инструментов (репликой ученика «Данных достаточно. Ответь коротко…», потому что хвост из `tool`-сообщений провайдеры без `tools` не ждут) и отдаёт настоящий ответ по собранному; не успел / сломалась / снова полезла в инструменты — честный 502 с бесплатным повтором и возвратом жетона (шаблонного `LONG_TURN_TEXT` больше нет — говорить может только модель). Замер живой: 3 вызова, 14.5 с, 10 шагов, полноценный ответ.
- **Явный `tool_choice: "auto"` не шлём** (`_chat_via_message`): умолчание OpenAI и так auto, а closerouter (маршрут anthropic) на многошаговом разговере с инструментами отвечает на явный auto 400 — замер 29.09 на одном и том же хвосте из `tool`-сообщений: auto → 400, без поля → 200 с вызовами, `required` → 200. Явные `required`/`none` шлём как есть. Заодно это убирает лишний запрос в failover в начале каждого хода агента.
- **Характер и живой язык — часть требований к промпту, а не украшение.** `AGENT_SYSTEM` (`server/agent.py`) задаёт не только правила, но и голос: ИИ говорит как человек, который рядом («на «ты», короткими фразами, обычными словами»), без канцелярита и без лести; явные запреты — «Конечно», «Разумеется», «Я готов помочь», пересказ вопроса своими словами, сюсюканье («молодец!»), пачка смайликов, жаргон («изи», «мотивашка»). Отдельное правило — реакция на «я тупой»/грубость: не морализировать, признать сложность, предложить один маленький шаг. Числа по-прежнему только из инструментов или стартового блока хода, имя — из стартового блока (инструмент ради имени не нужен), род или нейтрально.
- **Кнопки-продолжения под ответом — слова модели, а не форма.** Модель дописывает в конец ответа служебный блок ```` ```suggest ```` с 1–3 вариантами `{label, ask}`: `label` — любой текст кнопки (хоть «я умный»), `ask` — готовый вопрос от лица ученика, именно он уходит на сервер (название кнопки в чат не отправляется). Формат блока строгий (иначе не разобрать), содержимое — свободное; пример в промпте абстрактный (`<текст кнопки>`), чтобы модель не копировала его как шаблон. `agent.split_suggestions` вырезает блок из текста (в ленту и в базу он не попадает — это проверяется тестом) и отдаёт варианты в `suggests` ответа `POST /api/agent/turns` и `/turns/confirm`; понимается и JSON-массив, и построчный список `label | ask`, дубли по `ask` схлопываются, максимум 3. Шаблонных подстановок нет нигде: блока нет — кнопок нет (пустой список), а не дежурный набор. Настоящие кнопки хранятся в `agent_messages.suggests_json` рядом с ответом (миграция — `ALTER TABLE ADD COLUMN`, со старой базой всё работает через запасные ветки без колонки), поэтому история показывает те же слова модели, что были вживую. **Порядок истории — строго по ленте:** раньше пузыри пользователя рисовались сразу по ходу цикла, а карточки ответов — пачкой после него, и при N ходах все вопросы сбивались в кучу наверх, а все ответы — вниз (живой баг с прода: `UUU…AAA…` вместо `UAUA…`, при одном ходе незаметно). Теперь группы несут `kind: user/answer` и рисуются в порядке сообщений из базы; проверено на копии прод-треда из 77 строк — строгое чередование на всех 26 ходах, на старом коде тот же замер даёт `UUU…AAA…`. Регресс — `test/agent-ui.js`. Запрет ответов в кнопках ужесточён живым случаем: после выдачи задания модель положила правильный ответ внутрь кнопки («Проверь мой ответ: 12313») — теперь правило называет это нарушением прямо с примером и мотивом (кнопка с ответом убивает учёбу).
- **Нажатие кнопки: она уходит, соседние уезжают на её место, фокус не остаётся.** `collapseAsk()` (js/agent-spa.js) фиксирует ширину в px, схлопывает её и `margin-right` (двигает flex-соседей), затем убирает узел; `prefers-reduced-motion` — удаление сразу. Обводку снимает `b.blur()` руками (остаточный `:focus` выглядел как «кнопка залипла»), а клавиатурный `:focus-visible` оставлен. Пока идёт ход (`S.busy`), кнопка НЕ исчезает: сервер второй вопрос не примет, и человек остался бы без вариантов продолжения. При известном нуле квоты кнопка тоже не трогается (модалку открывает `send`). Протухший кэш (серверный 429 при кэше >0): вопрос не записан — кнопка возвращается на то же место (`restoreAskButton`, оба 429; `replaceLast` не трогаем — там ленту перечитывает `loadThreadMessages` и кнопки пересобираются сами).
- **Одно действие — ОДНО подтверждение (живой случай, чат 52).** Ученик: «смени моё имя на Артем» → `update_profile` встал на подтверждение, ученик нажал «Применить» — и resume цикла **запросил то же самое второй раз**; имя менялось только после второго подтверждения. Причина: `POST /api/agent/turns/confirm` собирал историю как `history[:-2]` с комментарием «модель продолжает с результатом» — но эти два сообщения (assistant с вызовом + tool с `{proposal, applied}`) как раз **отрезались**. Модель видела только просьбу ученика без следов выполнения и честно просила то же действие снова. Теперь история передаётся целиком, и модель видит `applied`. Проверено двумя способами: тест с моком, который **сам повторяет вызов, пока результат не виден** (на коде с багом — 5 падений из 5 проверок сценария, на новом 0), и сверкой переписки, где шаг `update_profile` должен быть ровно один.
- **Отмена зовёт модель, переделка плана — новое предложение.** Кнопка «Отмена» больше не пишет шаблон «Отменено. »: confirm делает 1 запрос к модели без инструментов с пометкой об отмене в контексте (стоит 1 жетон; без жетона/сбое — старый шаблон). «Поменяй темы / переделай план» больше не упирается в переспрос: сценарий промпта требует сначала plan_get (что сейчас в плане), затем plan_draft + plan_apply новым предложением (отменённый черновик — не запрет). Проверено в `test/ai-agent.py` (текст + кнопки модели в ответе на отмену, 1 жетон, запись в историю).
- **Перед новым планом — сначала взгляд на текущий (`plan_get`).** Агент умел ЗАПИСЫВАТЬ план (`plan_draft` + `plan_apply`), но не видел существующего: молча затирал текущий или переспрашивал то, что уже в базе. Новый read-инструмент отдаёт текущий план в ТОМ ЖЕ формате, что `plan_draft` (periods с темами skillId+название), плюс состояние каждой темы (done/open) и прогресс — отдельного «шаблона» нет осознанно: periods годятся в `plan_apply` как есть, для нового с нуля модель зовёт `plan_draft`. Человеческим языком сверху не дублируем: пересказ заставил бы модель перекодировать слова обратно в skillId с риском выдумать id. Сценарии промпта требуют `plan_get` первым при любом вопросе про план, но если в `КОНТЕКСТЕ ХОДА` строка «Учебного плана пока нет» — этот вызов пропускается и строй идёт сразу (экономия круга). Планы лежат по предметам, а «у меня есть план?» — без уточнения: плана в текущем нет, но есть в другом — инструмент отдаёт сводку `otherPlans` (предмет человеческим названием, срок, прогресс) и запрещает выдумывать «план в школе»; деталей чужого предмета там нет осознанно (его skillId текущий каталог отвергнет) — они живут в чате того предмета. Та же строка есть в `КОНТЕКСТЕ ХОДА`. Живой случай: план в обществе, вопрос из математики → было «плана нет — чистый лист» при живом плане. Проверено в `test/study-plan.py` (пусто/есть/шаблон в `plan_apply`/строка контекста/рез длинного плана/чужой предмет).
- **План от ИИ — функция Plus (08.10).** Создание и применение плана (`plan_draft`/`plan_apply`) — только с активной подпиской (`agent.plan_access_allowed` = активная подписка; от флага `EGE_AGENT_REQUIRES_PLUS` не зависит, тот закрывает весь ИИ): бесплатному инструменты выпадают из списка модели в `run_cycle`, а прямой вызов (`execute_read_tool`/`propose_action`/`apply_action`) отклоняется текстом про Plus, в том числе подтверждение после окончания подписки (предложение не применяется). Просмотр текущего плана (`plan_get`) остаётся бесплатным — план лapsed-пользователя виден и в профиле, и в чате. В `turn_context` бесплатному идёт строка «Тариф ученика: бесплатный…» — модель знает тариф, объясняет про Plus и не обещает план. `/api/subscription/status` отдаёт `limits.planAccess`, `js/subscription.js` — `cachedPlanAccess()`, и пустой чат ИИ не показывает подсказку «Составь план подготовки на неделю» без доступа. Регресс — `test/study-plan.py` (секция 9), `test/subscription.py` (planAccess), `test/study-plan-ui.js` (секция C).
- **«Стоп» останавливает и серверный ход (08.10).** Раньше кнопка рвала только запрос вкладки: сервер продолжал считать ход и держал слот треда до 95 с, поэтому новый вопрос или «Изменить» упирался в AGENT_BUSY и карточку «ИИ ещё отвечает…» — живая жалоба на 94-секундный ход (ПК: подписка истекла за 11 с до вопроса → бесплатный тир → opencode в таймаут → telegram с заблокированным ключом → funpay всё же ответил). Теперь клиент после «Стоп» шлёт `POST /api/agent/turns/cancel` (fire-and-forget): сервер отдаёт слот СРАЗУ, помечает токен хода отменённым (`_agent_turn_cancelled`), и ход, доработав текущий вызов модели, завершается через `AgentTurnCancelled` — без записи ответа/шагов, с возвратом жетонов. Слот хранит токен: остановленный ход не может снять слот нового хода того же треда. Композер свободен сразу, обрыв без отмены (сеть, перемонтирование) сохраняет старое поведение watchAnswer. Регресс — `test/ai-agent.py` (секция «Стоп» с медленным моком: cancel отдаёт слот, новый ход идёт, отменённый ответ не записан), `test/agent-ui.js` (клиентская стена).
- **Карточка подтверждения: без сырого кода, с блокировкой и без самоскрытия** (три жалобы на живом экране).
  - **Сырой вызов инструмента не показывается.** В шаге больше нет `<code>update_profile</code>` — правило 5b промпта это прямо запрещает («вместо fold_web говори словами»), а строку рисует сервер, модель её не контролирует. Подпись и так человеческая («Меняю профиль: 95+ баллов»), а технические детали живут в свёрнутом «Подробнее» с аргументами.
  - **Подтверждение держит блокировку хода.** `confirmStep` — это тоже ход (сервер применяет действие и зовёт модель, до 90 с), и раньше композер на это время оставался свободным: «Стоп» пропадал, поле принимало текст, и следующий вопрос упирался в `400 AGENT_BUSY` — то есть человек отправлял сообщение и получал ошибку на ровном месте. Теперь `confirmStep` заводит полноценный `S.turn` с `AbortController`, поэтому блокировка, «Стоп» и отмена работают тем же кодом, что и для обычного хода.
  - **Карточка, ждущая подтверждения, не сворачивается.** Лента с кнопками «Применить/Отмена» — это то, что человек сейчас должен нажать, а она через ~4 с сама схлопывалась под «Показать шаги», и приходилось раскрывать заново. `collapse()` и ветка истории теперь проверяют `needs_confirm` и оставляют такую карточку раскрытой (иначе то же самое происходило после перезагрузки чата).
  - Регресс — `node test/agent-confirm-ui.js` (живой Chromium, подтверждение намеренно замедлено до 2.5 с: проверяет отсутствие кода в видимой части шага, живость кнопки «Применить» через 9 с, блокировку композера во время подтверждения и то, что сообщение в этот момент не уходит) и `node test/agent-ui.js` (контракт по коду).
- **Карта возможностей, а не стресс-тест: `test/agent-capabilities.py`.** `agent-stress.py` ищет СБОИ, этот — отвечает на вопрос «на что ИИ СПОСОБЕН»: 26 способностей (чтение данных / действия / гибкость), у каждой проверяемое условие и вердикт `ок`/`частично`/`нет` с указанием, чем именно ограничено. Ход, который не состоялся (503/502), даёт **пропуск**, а не вердикт: провайдер недоступен — это внешняя помеха, и пустой ответ проходил бы половину проверок (в первом прогоне так набралось 13 ложных «успехов»). Мелочи, на которых тест споткнулся: переменная мока не должна называться `st` (выше уже есть `st` ответа — замыкание схватит его, и каждый ход упадёт с TypeError); проверки пишутся как `lambda r: cond or "текст"`, и такой лямбдой нельзя пользоваться напрямую (`cond or "текст"` истинно ВСЕГДА) — есть `_split`, который разбирает исходник и пересобирает чистую проверку.
- **Человеческое «хочу» — это запрос на изменение профиля (живой замер карты возможностей).** «Зови меня Катя» — ИИ просто поздоровался новым именем и профиль НЕ поменял (человеку кажется, что поменял); «хочу набрать 95+» — разобрал разрыв до цели, но и не предложил её поставить. Оба случая закрыты промптом (правила 6a и 6a2): формулировки «зови/назови меня», «хочу набрать/цель/уровень» — это `update_profile` с подтверждением, и порядок «сначала инструмент, потом слова». После правки сценарий «зови меня Катя» проходит.

- **Ссылки в ответе — та же разметка, что жирный/курсив, но фирменной кнопкой.** Модель пишет обычный markdown `[текст](https://…)`, ученику это должно выглядеть частью интерфейса, а не чужой веб-страницей. Четыре решения, каждое из которых ловится только замером:
  1. **DOMPurify режет `target` по умолчанию** — ссылка открывалась бы поверх приложения и человек терял переписку. `hardenLinks` ставит внешним `target=_blank` + `rel=noopener noreferrer` после санитайзера, внутренним — ничего лишнего (класс `--int`, пунктир: это подготовка к базе знаний).
  2. **Цвет текста — `--accent-ink`, а не `--accent`**: у чистого акцента контраст 3.51 на белом, то есть ниже AA (замерено; сам проект об этом предупреждает). С `ink` — 5.43. Рамка и подложка остались на `--accent`: они не текст.
  3. **Голый адрес приходит ссылкой из двух источников** — из markdown (gfm делает ссылку из «https://…» сам; это выяснилось при замере, сперва здесь была ошибка, будто он автолинкует только `www.`) и из `autolinkBareUrls` как страховка. Поэтому «подпись = сам адрес» определяется ПО ТЕКСТУ ссылки, а не по её классу: такие адреса длинные, и заглавными «HTTPS://OBRAZOVAKA.SDAMGIA.RU/…» нечитаемы — они получают `--raw` и остаются как есть. Внутри существующей ссылки и `code` автолинк не лезет.
  4. **Подпись кнопки — заглавными** («САЙТ ФИПИ», «МОЙ ПРОФИЛЬ»): плашка читается как действие, а не как строчка текста. Исключение — ссылка, подписью которой служит сам адрес.
  5. **В подписи только название, служебных слов нет** («ФИПИ», «КОДИФИКАТОР И СПЕЦИФИКАЦИЯ», «МОЙ ПРОФИЛЬ»): кнопка сама показывает, что это ссылка, а «САЙТ ФИПИ» / «ОТКРЫТЬ МАТЕРИАЛЫ» / «ПОДРОБНЕЕ ТУТ» — шум. Правило есть и в промпте (5f), **но модель его нарушает** — на живых вопросах подряд выдала `[ОТКРЫТЬ МАТЕРИАЛЫ ФИПИ]`, поэтому `trimLinkLabel` срезает крайние служебные слова из подписи у нас (наша кнопка, наш текст). Режет ТОЛЬКО края: «ОЦЕНКА СОЧИНЕНИЯ ФИПИ» цело, потому что ФИПИ здесь часть названия. Если после обрезки пусто — показываем имя сайта, пустой кнопки не бывает.
  6. **Печать по словам внутри ссылки ломает плашку** — отдельные слова встают по своей базовой линии. `buildTypedDom` относит саму ссылку к элементам печати: она проявляется целиком, в общем темпе с текстом.
  Промпт (правило 5f) требует: ссылка должна быть ТОЧНОЙ (никаких «примерно на fipi.ru/…»), подпись — словами, не больше одной-двух на ответ, и если уверенного адреса нет — честно сказать словами, а не оставить пустую ссылку. Живой замер: «Дай официальные материалы ФИПИ по сочинению» → `[официальном сайте ФИПИ](https://fipi.ru)`. Регресс — `node test/agent-links-ui.js` (9 проверок вживую в Chromium, включая контраст и вырезание опасной схемы).
- **Ошибочный аргумент инструмента больше НЕ убивает ход (живой замер: 6 ходов из 20 умирали `400`).** Модель обязана угадывать `skillId`/`taskId` (легенды id нигде не было), и любой промах раньше летел в `AgentInputError` → `400 AGENT_TOOL_ERROR` ученику: «объясни тему производные», «объясни задание 17», «посмотри мою ошибку по сочинению», «поменяй цель на 95+» — обычные вопросы, обычные ответы «ошибка ИИ». Пара `assistant(tool_calls)+tool` пишется в обоих случаях — иначе следующий запрос ушёл бы с «висящим» вызовом без ответа. Лимит `MAX_TOOL_RETRIES` (4), дальше — честный `_summarize` по собранному. Тест `test/ai-agent.py` переписан под новый контракт; старый «битый op → 400» больше не поведение.

- **`resolve_error` не имеет права закрыть не ту ошибку.** Три защиты: (1) если названы и `errorId`, и `taskId`, они обязаны указывать на ОДНУ строку; (2) уже разобранная строка отклоняется, а `apply_action` пишет `AND resolved=0` — раньше он отвечал `resolved: true` на строке, которая УЖЕ была `1`, и ученик видел зелёную галочку вхолостую; (3) подпись действия человеческая («Отмечаю разобранной ошибку по теме «…»») — `topic` берётся из базы, id туда не попадает.

Открытие переписки (`loadThreadMessages`) тоже сверяет кольцо из того же ответа. Регресс — `test/agent-ui.js` (контракт) + `test/ai-agent.py` (квота убывает уже во время хода).
- **Окно квоты ИИ — общая модалка приложения (`openAiLimitModal`), а не своя сборка.** У раздела ИИ была своя `.dlg`-окно лимита, собранная руками: другой вид, чем окно лимита проверки сочинений и инфо-диалог о модели на ege-result. Теперь это тот же `openAiLimitModal` (третий аргумент `opts` — текст, иконка, надзаголовок, подпись таймера, склонение, своя функция обновления квоты), поэтому вид, крестик, Esc, тап по фону, живой таймер и перезапуск по нулю у всех один. **Три тонкости, которые стоили отладки:** (1) локальную константу в `openAiLimitModal` нельзя называть `plural` — она перекрыла бы глобальную функцию в своём же инициализаторе (`pluralFn`, переполнение стека); (2) справочный режим (`timer: false`, кнопка «Закрыть») — это РОВНО инфо-диалог о модели, так что клик по кружку квоты даёт тот же вид, а не тост в углу (тост жил 2.6с, ничего не объяснял и перебивался другим; теперь его нет); (3) окно лимита агента переоткрывается с тем же `opts`, поэтому по нулю таймера спрашивается свой endpoint (`refresh: fetchQuota`), а не лимит сочинений. Проверено вживую: клик по кружку — надзаголовок «ИИ», имя «Осталось 10 из 10», текст про ход-запрос и зарядку третями, без таймера, кнопка «Закрыть», ноль тостов; Esc и крестик закрывают; `test/ai-limits-modal.js` (окно сочинений не изменилось) — ALL OK. В кружке цифры нет — только кольцо (остаток показывает окно по клику и aria-label). Регресс — `test/agent-ui.js`.
- **При нулевой квоте отправка закрыта заранее, а лента не трогается (`quotaOut`).** `syncInput()` дизейблит синюю кнопку (тот же серый `:disabled`-стиль) и меняет плейсхолдер на «Ходы закончились…», `setQuota()` дёргает `syncInput()` сама — состояние кнопки следует за квотой без ручных вызовов. `send()` при известном нуле не идёт в сеть и не трогает DOM: раньше заменяющий ход (перегенерировать/исправить) оптимистично сносил с экрана удачный ответ, а сервер при 429 старую пару не сносил — оставались два вопроса подряд без ответа. Тихие повторы (`quiet`) гейт пропускает — это догрузка показанного хода, а не новый вопрос. Страховка на случай протухшего кэша квоты — те же 429-ветки `settleTurn`: пузырёк снимается, а при `replaceLast` лента перечитывается (`loadThreadMessages(true)`). Пилюля «Осталось N из M» удалена полностью (элемент, CSS, все упоминания) — прятать её было бесполезно: на тач-тапе совместимый mouseenter приходит ДО click и возвращал её, а следующая setQuota ставила display заново, и при остатке > 0 она всплывала снова. Текст остатка живёт только внутри окна и в aria-label кнопки (в кружке цифры нет — только кольцо). Проверено вживую в мобильном Chromium (цифры нет в DOM, ховер/тап дают только окно). Регресс — `test/agent-ui.js`.
- **Исчерпание показывает окно само, когда допечатан последний текст.** Ход с финалом, потративший квоту в ноль (`usage.cost>0`, остаток 0), взводит флаг в settle (`armLimitModal`) — стреляет он в конце печати ответа (`fireLimitModal` в концах `revealTurn.actions` и обоих `next`), окном ровно тем же, что по клику на круг (`clickQuota`: свежий `fetchQuota` + та же ветка). Раньше конца печати (поверх недописанного) — никогда; при pending (подтверждение вместо ответа) и при отмене (cost 0) — никогда; перезагрузка при нуле сама окно не открывает (триггер — только что допечатанный ход). Снятие флага — новый вопрос, уход в другой чат, пересборка экрана; гонка «опрос старше финала» закрыта тем же `busy`-гейтом, что у живого кольца. Регресс — `test/agent-ui.js` (контракт) + `node test/agent-limit-modal-ui.js` (10 живых проверок: порядок «допечатка → окно», текст = окну по клику, reload молчит).
- **Внутренние коды в ответе — мягкое «лучше не надо», а не запрет** (правило 5b в `AGENT_SYSTEM`): вместо «задание **re_3_4**», `n01_planimetry`, `fold_web` модель говорит словами («задание на отрезки», «урок по производным»). Код уместен, только если ученик сам его прислал или просит найти именно его. Формулировка мягкая намеренно: жёсткий запрет в этом промпте уже есть (правило 5, «без нужды»), и он не спасал — модель всё равно выдавала id в начале фразы.
- **Кэш раздела — как у остальных экранов (`AdminInbox`), в памяти вкладки.** `S.cache = { accountId, threads, messages }`: список чатов и переписка открытого чата (`MAX_CACHED_THREADS` = 6 тредов) рисуются мгновенно при возврате на `#/ai`, а сеть только молча сверяет их на фоне — `sameMessages` не даёт перерисовать ленту без изменений, иначе у человека слетали бы раскрытые «Подробнее» и позиция прокрутки. Кэш привязан к аккаунту (`cacheDrop()` в ветке смены `S.accountId` — чужие чаты не показываем) и выбрасывается там, где переписка меняется: ход (`settleTurn`), подтверждение действия, удаление чата, 404. Локальные правки списка (новый чат, заголовок из первого сообщения, удаление) сразу кладутся в кэш, иначе возврат на раздел показывал бы список без только что созданного чата.
- **Читаемость текста чата: свои чернила раздела.** Общие `--text-2`/`--muted` рассчитаны на белые карточки, а чат стоит на фоне приложения (`--bg`): в светлой теме серый текст шагов читался «пыльным» (6.1:1 и 5.1:1), в тёмной `--muted` вообще не дотягивал до AA (4.2:1 — мелочь вроде дат и «Подробнее»). У `.agent` свои два оттенка с запасом по контрасту на фоне самого чата: светлая `--agent-ink-2 #384563` (8.1:1) и `--agent-ink-3 #465270` (6.6:1), тёмная `#c2c8da` (11.7:1) и `#949cb0` (7.1:1) — тот же смысл, тот же порядок ролей, контраст считает `test/agent-ui.js` по-настоящему (WCAG-математика по значениям из обоих CSS), так что вернуть серый назад молча нельзя. Ответ при этом со списками не слипается: `.agent__answer { white-space: pre-line }` — одиночный перевод строки внутри абзаца раньше схлопывался.
- **«Плохо видно в светлой теме» — это НЕ цвет (замерено, правка цвета не помогает).** Жалоба «текст агента плохо видно в светлой теме, а когда-то уже меняли и не помогло» — вторая попытка по цвету, поэтому сначала ЗАМЕР, и он перевернул диагноз. Замеренные числа (живой браузер, компьютированные стили, контраст по фактическому фону): ответ ИИ `--text #1b2233` на `--bg #e9edf4` = **13.5:1** — с запасом выше AA, цветом там нечего улучшать; затемнение цвета до `#101728` двигает плотность знака на **+0.04%** (ноль на глаз) — ровно потому прошлая правка и не сработала. Настоящие рычаги другие, и оба применены в `css/agent.css`: (1) **сглаживание** — общий `-webkit-font-smoothing: antialiased` на `body` на СВЕТЛОМ фоне выключает субпиксельное сглаживание, штрихи теряют толщину, и тёмный текст выглядит бледнее своего цвета; у раздела в светлой теме `auto` (субпиксель), в тёмной `antialiased` (субпиксель даёт цветные каёмки — это единственное место, где тёмная тема оставлена как была); (2) **кегль** — `.agent__answer { font-size: 16px }` вместо унаследованных 15px (ответ — длинный текст для чтения; шаги и мелочь остаются 14/12-13px, им хватает). Итог замером в одинаковом кропе: плотность знака **10.22% → 11.03% (+0.81%)** — в 20 раз больше, чем давал цвет. Правка ЛОКАЛЬНАЯ для `.agent`: общее правило темы в `styles.css` не трогаем (иначе менялся бы рендер всех экранов), и `test/agent-ui.js` проверяет и сглаживание в обеих темах, и кегль, и что глобальное правило осталось нетронутым. Правило на будущее: **видимость текста сначала меряется, потом чинится** — «контраст выше AA» означает, что менять цвет бесполезно, и смотреть надо на рендинг и кегль.
- **Закрепление экрана агента: единая поверхность без карточки, скроллится только лента.** Раздел — не карточка внутри карточки, а колонка между шапкой приложения и нижним меню: `.agent { display: flex }` (на десктопе — рейл тредов слева + область чата справа, на телефоне — колонка), `.agent__main` — обычная flex-колонка без фона/рамки/скругления, `.agent__toolbar` и `.agent__composer-zone` — `flex: none` с `border-bottom`/`border-top`, `.agent__feed` — `flex: 1; overflow-y: auto`. Тулбар и композер стоят на месте при любой прокрутке, крутится только лента.
  - `--bottomnav-h` меряет `syncTopbarHeight()` в `js/app.js` рядом с `--topbar-h`: на телефоне нижнее меню `position: fixed` и **перекрывает** низ экрана, поэтому его высота уходит в `padding-bottom` у `.screen--agent` (резерв); на десктопе меню скрыто (0) и резерв схлопывается сам. Без этого резерва баг был с обеих сторон: поле ввода уезжало под меню, а верх упирался в край.
  - `.app:has(.screen--agent) { height: var(--vv-h, 100dvh); overflow: hidden }` — на разделе агента страница не скроллится вовсе, иначе шапка уезжала из вида и весь раздел поднимался вверх. Высота берётся из `--vv-h`, который отдаёт `visualViewport.height` (`syncViewport()` в `js/agent-spa.js`): клавиатура на iOS сжимает видимую область, а не layout viewport, и без этого браузер скроллил документ, чтобы показать фокус.
  - **Пинить высоту колонки в пикселях на `focus` нельзя**: iOS скроллит страницу к полю, `blur` снимает пин — и страница уже не возвращается (поле «съедено»). От `focus` требуется ровно одно — обнулить резерв под меню (`--agent-bottom: 0` + класс `kb-open` на `:root`, потому что `var()` читает `.screen--agent`, а custom property вверх по дереву не поднимается).
