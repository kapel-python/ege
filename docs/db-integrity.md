# Целостность базы (SQL-инъекций нет, но дыры вокруг были)

## Целостность базы (SQL-инъекций нет, но дыры вокруг были)
- **Аудит не нашёл ни одной SQL-инъекции.** Все 41 f-string-вставка в SQL — структурные: идентификаторы приходят из литералов и констант модуля (`_MUTABLE_PK_REBUILDS`, `_IDEMPOTENT_UNIQUE_INDEX`, `catalog_columns`), а значения всегда параметризованы. `LIKE`-паттерн строится конкатенацией только из id каталога, не из запроса. Проверять это стоит при добавлении новых таблиц — правило: **в SQL из f-string попадает только имя из серверного литерала, никогда из тела запроса**.
- **Порядок ЗНАЧЕНИЙ = порядок плейсхолдеров.** В `agent.propose_action("resolve_error")` стояло `(task_id, subject, user_id)` при плейсхолдерах `(task_id, user_id, subject)`: инструмент не находил ошибку **никогда** (а как только `subject` смог бы стать числом — выбрал бы чужую строку, и `apply_action` с верным порядком пометил бы чужую ошибку разобранной). Ошибка такого рода невидима: код возвращает честное «ошибка не найдена».
- **`/api/health` — анонимный и читает ВСЮ базу.** `PRAGMA quick_check` проходит по всем таблицам и индексам. Раньше он был единственным `/api/`, снятым с общего per-IP бакета, то есть один адрес запускал полное сканирование 30 раз в секунду (столько держит `limit_req` в nginx), а ботнет — десятки параллельных. Теперь у него свой мягкий предел (`HEALTH_RATE_MAX` = 30/мин, хватает и мониторингу) и **кэш на 30 с** (`db_integrity()`), так что пачка запросов не превращается в пачку сканов. Тот же приём обязателен для любого нового анонимного тяжёлого эндпоинта.
- **Пересборка таблиц обязана быть в одной транзакции.** `DROP TABLE` + `ALTER ... RENAME` при автофиксации Python коммитятся раздельно: падение между ними оставляло таблицу **удалённой**, а следующий старс спотыкался о «already exists» — и каждый запрос отдавал 500 до ручного ремонта. Теперь `BEGIN IMMEDIATE` вокруг пары (`_MUTABLE_PK_REBUILDS`).
- **Миграция не имеет права «успешно» потерять строки.** `_support_relax_source_check` переносил обращения через `INSERT OR IGNORE`, который глотал нарушения `NOT NULL`: если в старой таблице нет `request_key`/`message_digest`, отбрасывались **все** строки, а `DROP` шёл следом — лента обращений исчезала без ошибки. Теперь недостающие ключи досыпаются (`randomblob`), а перед `DROP` сравнивается число строк: не совпало — откат, оригинал цел.
- **Миграция с записью внутри ensure обязана коммитить свою неявную транзакцию сама.** Бэкфилл `public_id` делал UPDATE внутри `ensure_subscription_schema`, а финальный `if not conn.in_transaction: commit` видел открытую транзакцию и пропускал коммит — `close()` откатывал UPDATE молча, и строки оставались без `public_id` навсегда (поймано тестом: прямой вызов с ручным коммитом работал, HTTP-путь — нет). Правило: мутатор внутри ensure коммитит, только если транзакцию открыл он сам (`own = not conn.in_transaction`), иначе — за вызывателем.
- **После пересборки состав колонок читается ЗАНОВО.** Снимок `_table_columns` до `_support_relax_source_check` считал `source` отсутствующим, и следующий шаг добавлял его повторно (`duplicate column name`).
- **UNIQUE-индексы для `ON CONFLICT` создаются не только при первом создании таблицы.** Таблица от старой версии без индекса роняла каждую запись с `ON CONFLICT clause does not match any PRIMARY KEY or UNIQUE constraint` — навсегда. `ensure_essay_schema` теперь чинит индексы и в ветке «таблица уже есть» (тот же самовосстанавливающийся приём с `try/except sqlite3.Error`, что в `_backfill_append_client_ids`).
- **Сброс «весь прогресс» обязан быть полным.** `load_essay_check` ищет ответ по `(user_id, subject, task_id, sha256(текста))` и **не требует** `essay_submissions`, поэтому выживший `essay_checks` отдавал бы прежнюю оценку бесплатно и навсегда. В списке сброса теперь есть `essay_checks`, `essay_check_history` и `activity_events` (последний читает ИИ через `fold_web op=history`). `task_id` в ключе — осознанно: оценка содержания считается под проблему задания, и без него один текст в пяти заданиях получал одну оценку без вызова модели (живой случай 03.10: пять ready с одной 21). Миграция: колонка + замена UNIQUE-индекса + бэкфилл задания по earliest-submission (создавал проверку самый ранний submission — поздние брались из кэша).
- **Бюджеты защищены правильно.** `ai_usage_try_reserve` / `agent_quota_reserve` начинают с записи (`INSERT OR IGNORE`), берут RESERVED-лок на всю неявную транзакцию, а уменьшение идёт защищённым `UPDATE ... WHERE count>0` с проверкой `rowcount` — перерасхода на гонке нет. `domain_write` = `BEGIN IMMEDIATE` + CAS по `state_version`. XP пересчитывается из строк, клиентский `xp` игнорируется.
- **`ON DELETE CASCADE` покрывает все пользовательские таблицы** (включая `agent_threads`/`agent_messages`), поэтому `DELETE /api/state` полный. `PRAGMA foreign_keys=ON` ставится на соединение вне транзакции, и обе пересборки, которым нужен `OFF`, коммитят заранее — это не тихий no-op.
- **Секреты в базе — только HMAC.** `device_fingerprint_secret`, `support_form_secret` и отпечатки устройств/сети лежат хэшами; сырые IP и UA не появляются. Токены сессий — тоже: `user_sessions.token`, `admin_sessions.token` и легаси `users.session_token` хранятся как `sha256` (`token_digest()`), а не открытым текстом. Раньше чтение файла БД (или бэкапа) давало готовые куки — пара `ege_session` + `ege_admin` из файла открывала админку со всеми аккаунтами (проверено на живой базе: 94 сессии + 2 админские). Ключа не нужно: сам токен — 256 бит из `secrets.token_urlsafe(32)`, по хэшу не восстанавливается. Миграция `hash_stored_tokens()` идемпотентна и не рвёт живые сессии: поиск хеширует предъявленный токен, поэтому старая сырая кука даёт тот же хэш и работает (проверено: 87/87 живых + 2/2 админских, 7 нерядовых — сироты удалённых пользователей, их JOIN и не находит; сироты чистятся). Совместимость с легаси-строкой — tolerant-lookup в `session_row_for`/`admin_session_user` (находит по сырому и сразу переводит на хэш), чтобы восстановленный из бэкапа токен не умирал. Тесты, лезущие в SQL напрямую (`auth`, `auth-audit`, `admin-inbox-security`), обязаны хешировать через `server.token_digest`, а не подставлять сырой токен.
